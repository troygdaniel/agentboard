# Task: Map the call sites

Task ID: map-sites

## Before you claim: ask if anything's unclear

If this task is ambiguous, send your orchestrator/coordinating session (if you have one) a one-line
question — e.g. via SendMessage — and wait for its answer before claiming. It has visibility into the
whole board and can often answer without bothering the user; it escalates to them if it can't. This is
a one-time check before you start, not an ongoing back-and-forth once work is underway.

## Step 0: claim the parent (do this first)

This task is a subtask of "Refactor billing" (refactor-billing). It can only be worked while its parent is in
Doing, and claiming the parent takes all of its subtasks with it. Skip this if the parent is already yours.
Use your own session name:

    agentboard claim refactor-billing --name "<your session name>"

## Progress reporting

The percentage is what the board/HUD show at a glance, so keep it honest: your real % of this subtask,
updated whenever your estimate changes (it can go down). The parent's % is computed from its subtasks.

    agentboard update map-sites 30 "<what you are doing>"
    agentboard update map-sites 100 "<one-line result>"

A subtask at 100% closes itself: there is no review step for a subtask, so do NOT run `review` or `done` on it.
When the whole deliverable is ready (this and its sibling subtasks), review the PARENT:

    agentboard review refactor-billing "<one-line result>"

The USER signs off on the parent and moves the card to done. Run `agentboard done` ONLY if the user explicitly tells you to.
After you review the parent, do not sit idle: start `agentboard answer refactor-billing --wait --timeout 3600` as a background
command (in Claude Code, Bash with run_in_background) and end your turn. You are woken when the user replies, sends the
card back, closes it ("Done by the user"), moves it or removes it, and it prints what happened. A message the user sends you on
the board (your thread) wakes it too: answer with `agentboard chat send "<one line>" --name "<your session name>" --to the user`.
Between cards, stay reachable with `agentboard chat inbox --name "<your session name>" --wait 3600` in the background the same way.

If you are blocked on the user mid-task, flag it (and keep going once they answer):

    agentboard ask map-sites "<one-line question>"

The user answers on the card, not through anyone else. After you ask, do not sit idle: start
`agentboard answer map-sites --wait --timeout 3600` as a background command (in Claude Code, Bash with run_in_background)
and end your turn. You are woken when the user replies, and it prints their reply; then carry on. It also wakes when
the user sends you a message on the board (your thread, outside any card) and prints it: answer with
`agentboard chat send "<one line>" --name "<your session name>" --to the user`, then wait again. A tool that cannot
run background commands runs it in the foreground instead. If it times out with no reply, say you are still waiting.

Between cards, and any other time you would go quiet with nothing running, keep yourself reachable the same way:
`agentboard chat inbox --name "<your session name>" --wait 3600` as a background command. It prints the next line the user
sends you and exits, and that wakes you; nothing else does. The board shows who is listening, and a Stop hook reminds
a session that is about to go quiet without one.

These are not optional.

## When you review

Write the `--body` in this shape; the board lays it out on the finished card (keep what you have, skip the rest):

    ## Changed
    - up to four bullets: what is different now
    ## Checked
    - 675 tests pass · render-check wide and narrow
    ## Next
    - what the user must do, or: nothing
    ```flow
    You mark done -> Card gets a reply -> Agent wakes
    ```

A ```flow block is a small diagram: `A -> B -> C` draws boxes and arrows, `label: 12` draws a bar. A card without this
still shows what the board knows (subtasks, tests it can find, commits).
## Reporting to the user

Report to the user in one sentence, one idea: the ACTION they must take first, then one fact. If nothing is needed from them, one line of
status. If more is unavoidable, one sentence, then offer the detail. Put that sentence on the card (agentboard ask/review/update text)
so the user answers you there, and in your terminal. Put detail in `--body` (it shows under Details on the card), never in the first line.

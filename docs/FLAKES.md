# Flaky tests

Tests that failed once and passed on a rerun of the same tree, why, and what was done. Written on 14 Nov 2026 from the 13 full suite runs found on one busy Mac (11 to 14 Nov, 590 to 890 s each, load average often over 80 on 10 cores) and the sightings of the people running them. A test is listed as a flake only with a cause that is about timing, load or the machine's sleep; a failure that goes with a branch's unfinished change is a failure, and is listed at the end so nobody spends time on it twice.

**Before you call something a flake:** run it alone (`python3 -m unittest tests.test_x.Class.test_name`). If it passes alone and the failure says timed out, refused, missing or 'not found' under load, it is likely here. If it fails alone, it is yours. Run the whole suite alone too: other suites on the machine make the timing tests worse.

| Test | Symptom | How often | Cause | Fix or workaround |
|---|---|---|---|---|
| `test_workprofile` `TheLinesSayExactlyWhatWasChecked.test_the_flood_line_counts_held_and_refused_apart` | `'30 more were refused with 503' not found`: the line says 28 or 29 refused and one more request | 4 of 13 full runs, always on a busy Mac | The flood check (`selfcheck.py`) opens 158 connections in a burst. The kernel queues at most 128 connections the server has not accepted yet (the server asked for Python's default of 5), and resets the rest; the check then read the sockets one by one with a 0.1 s wait each (over 15 s), so a late 503 or a reset counted as nothing. | **Fixed.** `server.py` asks for 256 (the OS caps it at 128). The check opens in groups of 16, reads all sockets with one `select`, counts a reset or closed socket as lost and tries the flood again (up to 3 times) when any were lost. Its pass condition is unchanged: exactly the cap held, at least one refused, a further request 503. `test_the_flood_line_holds_when_the_accept_loop_is_slow` slows the accept loop by 3 ms a connection: the old check failed 3 of 3 (65 to 84 held, none refused), the new one passes 3 of 3. |
| `test_workprofile` the tests that run `agentboard selfcheck` in a subprocess (`TheProfileSaysWhereItCameFrom`, `TheSelfcheck.test_the_command_prints_a_list_and_json`) | `subprocess.TimeoutExpired ... timed out after 60 seconds`, or an error from the same run | 2 of 13 runs (load average over 80) | A flat 60 s limit around a command that takes about 10 s on an idle Mac and more than 60 s when the machine is starved. The limit is there to catch a hang. | **Fixed.** `patient(60)` stretches the limit by the load per core (never under 60 s). A command that hangs still ends. |
| `test_runs` (any test that reads the recorded run file) | `FileNotFoundError` on the record the fake agent writes; "recorded run file missing" | Seen once, in a full run after the Mac had slept for about an hour (ORCH, 14 Nov) | `runs.py` timed a run's minute limit, the kill grace and the duration with `time.time()`. A sleep moves the wall clock: the 1-minute limit was used up at once and the run was stopped before the fake agent wrote anything. Real runs lost their minutes to a sleep the same way. | **Fixed.** `runs.clock = time.monotonic` (it does not tick while the Mac sleeps). `test_a_mac_that_sleeps_mid_run_does_not_use_up_the_minutes` jumps the wall clock an hour mid-run; its control gives the run a clock that ticks asleep and the limit stops it. |
| `test_no_reply` `TheListenerList` (the two tests that look at the listener list during a wait) | `KeyError: 'AGENT-4'` on the snapshot, or the message not found | Not seen failing in the logs that could be read (on the list from the owner) | Timers fired at a fixed 0.3 s and 0.6 s, but how long the waiting command takes to register depends on the load: the snapshot could come before the listener existed. | **Fixed.** `once_listening` polls for the listener, then snapshots and acts. The tests still check what they checked. |
| `test_chat_e2e` `LatencyPerAgent`, `ReceiptsTellTheTruth` (three tests) | `'seen' != 'delivered'`, `(nothing new)` instead of the shown-again line | Once: three tests in one run, 14 Nov 13:45 | The run was of a branch that was changing session receipts that day; not seen in the 8 full runs after it. | Not a flake until it recurs: counted as that branch's failure. If it recurs, look at how the session key (the first non-shell ancestor process) differs between the runner and the command. |
| `test_doctor` | none found | 0 of 13 runs; 3 of 3 alone | The file fakes `ps`, `lsof` and `git` and has no timing. | Nothing to fix. It was on the list because it failed in a run that was also failing for another reason. |

## Failures that are not flakes (so they cost nobody a second look)

- `test_docs_architecture` "every module is in the map" (2 runs), `test_owner` "names nobody" (1 run), `test_drag_everywhere`, `test_panel_tabs`, `test_reporting` (1 run), `test_init_profile` "every variable the source names" (1 run): each was a branch with its change unfinished (a new module with no row in `docs/ARCHITECTURE.md`, a new `AGENTBOARD_` variable not in `profile.CORE_ENV`, a page change not yet matched in its test). They failed alone as well. The fix was the branch's own.
- The whole suite takes 590 to 890 s on a busy machine and about 400 s on a quiet one; run it alone, as `CONTRIBUTING.md` says.
